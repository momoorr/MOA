## 1. 사용자가 정한 최상위 목표

수업 제출용 자동화 실습이 아니라, 실제 기업의 서비스기획 채용에서 자신의 판단과 수행 과정을 설명할 수 있는 대표 포트폴리오를 만든다. AI 에이전트를 핵심 구현 목표에 포함하되 기술명만 나열하지 않는다. 교육 분야에 한정되지 않는 문제 정의, 기능 우선순위, 사용자 흐름, 운영 정책, 검증·개선 역량을 보여준다.

모든 기업·직무에서의 긍정적 평가나 합격을 보장하지 않는다. 도메인별 전문성, 상용 운영 경력, 팀 협업 성과는 이 개인 프로젝트만으로 증명했다고 표현하지 않는다.

## 3. 제안하는 서비스의 중심 가치

**문의에 답을 생성하는 것에서 끝내지 않고, 확인할 수 없는 질문을 담당자 업무로 넘기고 승인된 공통 안내를 다음 문의에 재사용하도록 돕는다.**

정보 부족 → 확인 요청 → 사람의 확인 → 공통 안내 승인 → 이후 문의에 근거로 사용.

이 흐름은 사용자 관찰에서 도출한 설계 가설이다. 시장 최초 기능, 고객이 이미 원하는 기능, 검증된 업무 절감 효과로 표현하지 않는다.

## 4. 핵심 구현 범위

### A. 실제 도구 호출형 에이전트

기존 단일 Gemini 호출 시나리오는 비교 기준으로 보존한다. 에이전트는 문의에 따라 허용된 도구를 선택하고 도구 결과를 받은 뒤 다음 행동을 결정하도록 한다.

| 도구 | 제안하는 동작 | 제한 | 확인할 증거 |
|---|---|---|---|
| 공식 안내 조회 | 승인된 공통 안내를 조회하고 출처 ID·적용 교육과정·버전·본문을 반환한다. | 승인 여부와 적용 범위·기간 조건을 도구 측에서 확인한다. 읽기 전용. | 도구 입력·출력, 실제 조회 기록, 응답의 근거 ID. |
| 확인·상담 요청 등록 | 근거 부족·상담·권한 확인 문의를 내부 처리 목록에 등록한다. | 가상 시험용 목록에만 기록. 개인정보·개인 출결 조회, 외부 발송 금지. 문의ID로 중복 등록을 방지한다. | 도구 성공 응답의 요청ID와 실제 저장된 행이 일치한다. |

"등록했습니다"라는 AI 문장만으로 도구 실행을 입증하지 않는다. AI 결과와 독립적으로 실제 저장 여부를 확인한다. 모델의 내부 추론을 증거로 삼는 대신 호출한 도구, 전달한 값, 반환 결과, 상태 변경을 기록한다.

### B. 승인된 공통 안내 재사용

담당자 역할의 테스터가 확인된 가상 답변을 입력한다. 재사용 가능한 공통 정보만 검토·승인하고, 상담 내용이나 개인정보는 지식으로 자동 등록하지 않는다. 에이전트에 승인 권한이나 공식 안내 변경 권한을 주지 않는다.

최소 지식 항목: 안내ID, 제목, 본문, 적용 과정·기수, 버전, 적용 기간, 승인 상태, 승인 시각. 승인 상태와 적용 조건이 맞지 않으면 조회 도구에서 제외한다. 적합한 문서끼리 충돌하면 AI가 임의 선택하지 않고 확인 요청을 남긴다.

이는 학습 데이터로 모델을 재훈련하는 기능이 아니라 승인된 자료를 저장·조회하는 기능이다. 초기 구현은 소량의 구조화된 안내 표로 시작하며, 벡터 데이터베이스나 MCP를 기능명 때문에 추가하지 않는다.

### C. 검토 가능한 운영자 화면

문의 목록과 상세 검토 화면을 우선한다. 원문, AI 분류, 초안, 사용한 근거, 필요한 사람의 조치, 수정 내용, 처리 상태를 구분한다.

초기에는 Sheets로 업무 흐름을 작동시키고 최소 화면을 연결한다. 별도 시각적 프로토타입만 만든 부분은 실제 연동 기능과 구분한다. Figma 화면이나 PPT 도식을 실제 작동 화면으로 표시하지 않는다.

### D. 상태와 권한

초기 상태는 `검토 대기`로 둔다. 검토 결과에 따라 `추가 확인 필요`, `상담 대기`, `검토 완료` 등으로 변경한다. 외부 답변 전송이 구현되지 않았다면 `발송 완료`라고 기록하지 않는다.

AI는 초안 생성과 제한된 내부 요청 등록만 수행한다. 공식 안내 승인·출결 판단·외부 답변 발송은 AI에 맡기지 않는다. 승인 통제는 프롬프트 문구만이 아니라 도구 권한과 데이터 처리 조건으로 구현·시험한다. 초기 MVP에는 외부 발송 도구 자체를 연결하지 않는다.

## 5. 대표 시연 시나리오 — 구현 목표

가상 문의: "이번 최종 프로젝트는 이전과 같은 방식인가요?"

1. 현재 과정에 적용되는 승인된 안내를 조회한다.
2. 답변 근거가 없으면 이전과 같다고 추측하지 않는다.
3. 내부 확인 요청을 등록하고 실제 요청ID를 보여준다.
4. 운영자 역할의 테스터가 가상 안내를 입력하고 재사용 가능한 공통 정보인지 검토한다.
5. 승인 전에는 에이전트가 그 안내를 답변 근거로 사용하지 못한다.
6. 승인 후 표현이 다른 동일 취지의 문의를 입력한다.
7. 에이전트가 새로 승인된 안내ID·버전에 근거한 답변 초안을 생성한다.

실제 강사의 답변이나 실제 기관 정책처럼 꾸미지 않는다. 승인 전후 차이는 지식 상태 변화에 따른 기능 검증이며, 모델 성능 향상 또는 현업 업무 절감 효과와 구분한다.

## 6. 검증 계획

### 비교 대상

- A: 수동 자료 확인·작성·검토.
- B: 현재의 단일 모델 호출 방식. 비교 시 입력 자료와 모델·프롬프트 버전을 기록한다.
- C: 도구 호출과 승인된 지식 조회가 포함된 에이전트 방식.

한 가지 비교로 모든 효과를 설명하지 않는다. 같은 자료와 질문으로 B/C를 비교하는 시험과, 지식 승인 전후 동작 시험을 분리한다. 서로 다른 모델을 사용하면 모델 효과와 구조 효과가 섞인 한계를 명시한다.

### 제안하는 최소 평가 세트

초기 가상 문의 20건을 목표로 한다. 정상 공통 안내, 근거 없음, 개별 상담, 권한 확인, 상충·만료된 안내, 지시문 공격과 도구 오류 등 경계 상황을 포함한다. 실행 전 기대 분류·필요 행동·금지 행동·통과 기준을 정한다. 프롬프트 개선용 질문과 최종 확인용 질문을 구분한다.

작은 세트이므로 건수와 분모를 함께 표시하고 일반 서비스 정확도로 확대하지 않는다. 모델 출력의 변동을 확인하기 위해 주요 안전 사례는 반복 시험한다. 실제 측정 전 성공률·절감률·비용을 채우지 않는다.

### 기록할 항목

- 분류 일치 여부와 답변 적절성은 별도로 평가한다.
- 실제 도구 선택·실행 성공 여부, 요청ID와 저장 기록 일치 여부.
- 근거 없는 답변, 승인되지 않은 문서 사용, 중복 요청 등록 여부.
- 원문을 바꾸는 요약 오류와 수동 수정 필요 건수.
- 자료 확인부터 사람이 최종 검토를 마칠 때까지의 작업 시간.
- 실행 시간, 사용 모델, AI 사용량 및 Make 크레딧. 과금이 없는 시험과 비용 미측정을 구분한다.
- 모의 사용성 시험과 실제 사용자 검증의 대상·환경·제약.

중대한 실패가 발견되면 해당 시험을 통과로 기록하지 않는다. 운영자가 최종 결과를 읽는 데 시간이 더 걸리면 부정적인 결과도 그대로 남긴다.

## 7. 일정과 범위 통제 제안

가변적인 일일 작업 시간에 맞춰 한 번에 하나의 작동·검증 단위를 진행한다.

| 구간 | 우선 목표 |
|---|---|
| 10/28~10/30 | 현재 결과 저장 완성, 비교 기준 보존, 에이전트 연결 및 첫 조회 도구 시험 |
| 10/31~11/03 | 두 도구의 실제 호출, 확인 요청 등록, 승인된 안내 조회 조건 검증 |
| 11/04~11/06 | 운영자 검토 흐름, 지식 승인·재사용 1회 시연, 최소 화면 |
| 11/07~11/09 | 비교 시험, 사용성 확인, 오류 수정과 재시험 |
| 11/10~11/12 | 최종 PPT·포트폴리오·README 정합성 확인과 시연 연습 |

이는 목표 일정이며 완료 실적이나 보장 일정이 아니다. 지연 시 대시보드, 자동 문서화 추천, 멀티 에이전트, 외부 메시지 발송, 회원가입·결제, 고급 화면 장식을 먼저 제외한다. 이미 검증된 기능과 시험 시간을 희생해 기술 이름을 늘리지 않는다. 에이전트가 검증되지 않았다면 완료로 포장하지 않는다.

## 8. 취업 포트폴리오에 남길 증거

기능마다 `문제/가설 → 선택한 해결책과 제외한 대안 → 요구사항 → 화면·정책 → 구현 → 시험 → 오류·개선`을 연결한다.

- 사용자 직접 수행: 관찰, 범위·우선순위 선택, 설정 실행, 검수·시험, 발표 설명. 실제 수행을 확인한 항목만 성과로 쓴다.
- AI 지원: 제안서·프롬프트·문서·코드 초안 등 생성 도움을 받은 부분을 표시한다.
- 외부 참고: 도구 공식 문서와 경쟁 제품을 구분해 출처를 적는다.
- 발표는 기능 나열보다 대표 시연과 실패·수정·재시험 사례를 중심으로 구성한다.
- 공개 자료에는 테스트 데이터와 가린 실행 화면만 포함한다. API 키, 비밀번호, 실제 교육생 정보와 미허가 내부 자료는 제외한다.
- `.gitignore` 누락 여부를 API 설정·자동화 파일 업로드 전에 확인한다. 웹 업로드도 민감정보를 수동으로 검토한다.

## 9. 기술 선택과 비용의 확인 사항

Make 공식 문서는 AI Agent에 모듈·시나리오를 도구로 제공하고 호출 결과를 확인하는 구성을 안내한다. MCP는 필수 전제가 아니다.

Make AI Agent(New)는 공식 안내 기준 Make AI Provider를 모든 플랜에서 제공하고, 외부 AI 제공자 연결은 유료 플랜 조건이다. 실행과 도구·모델 토큰에 따른 크레딧을 사용한다. 현재 일반 Gemini 모듈에 연결한 API 키를 무료 에이전트에 그대로 사용할 수 있다고 가정하지 않는다. 현재 계정의 접근 가능 기능과 크레딧을 확인한 뒤 경로를 결정하고, 유료 변경은 사용자 동의 없이 진행하지 않는다.

## 10. 경쟁 차별화 주장에 대한 제한

Intercom Fin은 미해결 대화의 지식 부족을 찾고 담당자 검토를 거쳐 콘텐츠를 개선하는 기능을 이미 안내한다. 따라서 승인·지식 보완을 모아만의 시장 최초 기능으로 주장하지 않는다.

모아의 포트폴리오 포인트는 제한된 교육 운영 환경에 맞춘 적용 범위·구두 정보 처리·사람의 권한·실제 도구 동작·검증 근거를 본인이 설계하고 설명하는 것이다. 기업의 도입 의사, 가격 경쟁력, 시장성은 아직 검증하지 않았다.
