# MOA 기획 변경 및 기능 확장 기록

> **프로젝트:** MOA — AI 기반 기업교육 운영 문의 관리 서비스  
> **기록 기준일:** 2026-11-09  
> **문서 목적:** 개발 과정에서 드러난 문제, 의사결정, 변경 내용, 검증 결과를 서비스기획 취업용 근거로 정리  
> **자료 성격:** 개인 프로젝트의 가상 교육 운영 시나리오·테스트 기록. 실제 고객사 도입이나 운영 효율 개선 실적을 의미하지 않음.

## 1. 최초 기획의 중심 방향

교육생 문의를 유형별로 분류하고, 공식 자료에 근거한 답변 초안을 준비하되 **사람이 최종 확인한 뒤 사용**하는 운영 지원 서비스를 구상했다. 처음부터 다음 원칙을 중심에 두었다.

- **공통 안내:** 공식 자료에 답변 근거가 있을 때만 안내 초안 제공
- **정보 확인 필요:** 공식 자료가 없거나 확정되지 않은 사안은 추측하지 않음
- **개별 상담·권한 확인:** 개인별 판단 또는 개인정보 확인이 필요한 문의는 담당자에게 연결
- **사람의 검토:** AI 결과가 최종 발송으로 자동 연결되지 않도록 구분

개발 과정에서 바뀐 것은 이 원칙 자체보다는, **원칙을 실제로 지키게 만드는 검증·저장 방식**이었다.

## 2. 기존 구현을 수정한 사례

| 주제 | 초기 구현 또는 접근 | 확인된 문제 | 수정·재설계 방향 | 검증 상태 |
|---|---|---|---|---|
| AI 답변 근거 | AI가 안내자료를 참고하여 문장을 생성 | 공식 자료에 없는 `학습 관리`, `내 강의실` 등 메뉴명을 답변에 추가 | 프롬프트 제한을 보완하고, 승인된 안내를 다시 조회해 **안내 원문을 답변 초안으로 사용** | 재시험에서 과제 제출 안내 원문 사용 확인. 모든 유형의 오류 방지는 미검증 |
| 분류와 실행 행동의 정합성 | AI가 문의 분류와 다음 작업을 결정 | `정보 확인 필요`와 `USE_APPROVED_GUIDE`가 함께 반환된 사례 확인 | 정상 안내 경로에 `next_action = USE_APPROVED_GUIDE` **AND** `category = 공통 안내` 조건 추가. 근거 불충분 시 초안 보류 | 필터·Fallback 흐름 일부 확인. 전체 예외 회귀 시험 전 |
| 보류 문의 재처리 | 재처리 시 결과를 다시 저장 | 동일 문의가 별도 행으로 중복될 가능성 | 검색한 **기존 행 번호**를 기준으로 `Update a Row` 실행 | 기존 행 제자리 갱신을 개별 시험에서 확인 |
| 문의 식별자 | `MOA-FORM-` + Google Sheets 행 번호 | 시점별 원본 행 구성과 기존 저장 ID가 어긋나는 사례 확인 | Google Forms의 고유 `Response ID` 사용 검토 | Response ID와 문의 원문 조회 성공. v2 통합 전환 및 중복 검증은 **미완료** |

### 사례 A — AI가 공식 자료에 없는 내용을 안내함

**발견:** 과제 제출 위치를 묻는 가상 문의에 AI가 공식 자료에 없는 메뉴를 포함하는 응답을 생성했다.

**판단:** 단순히 AI에게 더 신중하게 답하라고 요청하는 것만으로는 근거 없는 안내를 충분히 통제하기 어렵다고 보았다. 답변을 자유 생성하기보다 **승인된 공식 안내의 내용 자체를 우선 사용**하는 구조가 필요했다.

**조치:** AI 지시문을 수정하고, Make에서 승인 상태의 안내ID를 다시 조회한 뒤 `approved_reply_text`에 안내 원문을 담도록 구성했다. 정상 안내 경로에서는 AI의 자유 서술 대신 해당 값을 저장하도록 매핑했다.

**검증:** 과제 제출 메뉴를 안내하는 문장으로 수정된 결과를 확인했다. 다만 다른 질문 유형 전체에서 환각이 방지됐다고 주장할 수는 없다.

### 사례 B — AI 분류와 실행 행동이 충돌함

**발견:** AI가 `정보 확인 필요`로 분류했는데도 실행 행동으로 `USE_APPROVED_GUIDE`를 반환하는 사례가 있었다.

**판단:** AI의 출력값 하나만 믿고 다음 단계로 진행하면 근거가 불충분한 문의가 공통 안내처럼 저장될 위험이 있었다.

**조치:** 정상 안내 경로의 조건을 분류·행동 **두 항목 동시 충족**으로 보완했다. 그 외에는 담당자 확인 또는 Fallback 처리하도록 분리했다. API 코드에도 분류·행동이 일치하지 않으면 자동 답변 초안을 보류하는 방어 로직을 작성했다.

**검증:** 관련 필터와 보류 경로의 실행 기록을 확인했다. 모든 조합·예외 상황에 대한 완전한 회귀 검증은 남아 있다.

### 사례 C — 동일 문의의 재처리 결과가 중복될 위험

**발견:** 처리 실패 후 같은 문의를 다시 다룰 때 행이 새로 추가되면 운영자가 하나의 문의를 여러 건으로 오인할 수 있었다.

**조치:** 대상 행을 검색한 뒤 해당 행에 `Update a Row`를 적용하도록 변경했다.

**검증:** 가상 문의에 대한 재처리 실행에서 동일 행 갱신을 확인했다. 다중 실행·동시 요청에 대한 중복 방지까지 입증한 것은 아니다.

### 사례 D — 행 번호 기반 문의ID의 한계

**발견:** `MOA-FORM-9`라는 저장 ID와 당시 Google Sheets 9행에 표시된 문의 내용의 대응이 시점에 따라 달랐다. 행 번호를 영구 식별자로 쓰면 원본 변경 또는 행 구성 변화에 취약하다는 점을 확인했다.

**검토한 대안:** Google Forms `Watch Responses` 모듈을 별도 시험하여 `Response ID`와 문의 원문(`Answers → textAnswers → answers → value`) 반환을 확인했다.

**현재 상태:** `MOA - Forms Intake Agent v2 ResponseID Test` 복제본을 만들고 전환을 시도했지만, 기존 `[1] Row number` 참조가 여러 모듈에 남아 매핑 오류가 발생했다. **Response ID 기반 전환은 아직 구현·검증 완료가 아니다.** 기존 정상 작동 시나리오는 보존했다.

## 3. 개발 과정에서 새롭게 추가·구체화한 기능

| 기능 | 추가한 이유 | 구현·검증 범위 |
|---|---|---|
| **실제 도구 호출형 AI Agent** | 분류 결과만 출력하지 않고 승인 안내 검색과 담당자 확인 요청이라는 후속 작업을 수행하기 위해 | `search_approved_guide`, `register_confirmation_request` 호출 및 요청 행 저장 개별 확인 |
| **공식 안내 승인 상태·버전** | 승인되지 않았거나 확정되지 않은 자료를 안내 근거로 쓰지 않기 위해 | 가상 안내 `MOA-G003`의 승인 전후 동작 시험. 실제 교육기관 정책 확정은 아님 |
| **Fallback / 확인 요청 관리** | 정답 근거가 없는 문의를 단순 실패가 아닌 운영자의 업무 대상으로 남기기 위해 | Make·Google Sheets 경로 구현. Supabase Fallback 저장은 별도 검증 필요 |
| **Supabase 공통 데이터 저장** | Sheets에만 남던 AI 결과를 운영자 웹 화면에서도 사용할 수 있도록 하기 위해 | Edge Function 경유 테스트 JSON 1건, 실제 AI 처리 결과 1건 DB 저장 확인 |
| **운영자 전용 조회·검토 API 및 로그인 UI** | AI 판단과 사람의 수정·승인 결과를 분리하고 접근을 제한하기 위해 | 코드 작성·배포 및 로컬 로그인 화면 표시 확인. 실제 로그인→조회→승인 저장은 **미검증** |
| **QA·커밋 이력 정리** | 기획 의사결정과 기능 변경의 근거를 남기기 위해 | GitHub 문서·커밋 기록 일부 확인. 최종 정리 지속 중 |

> **처음부터 있었던 원칙과 새로 추가한 기능 구분:** 담당자가 최종 검토해야 한다는 원칙은 초기 기획에 이미 있었다. 이후 새로 구체화한 것은 검토 상태 필드, 승인/보류 경로, 운영자 접근 제한, 실제 데이터 저장과 같은 **구현 방식**이다.

## 4. 구현 중 발생한 기술 오류와 검증

### Supabase 저장 실패 — `42501` 권한 오류

1. **현상:** Make에서 Edge Function을 호출했지만 `HTTP 500`, `Database write failed` 반환.
2. **원인 추적:** Supabase Edge Function 로그에서 PostgreSQL 오류 코드 `42501` 확인.
3. **점검:** `service_role`의 `INSERT`, `SELECT`, ID 시퀀스 `USAGE` 권한을 SQL로 조회했으며 모두 `false` 확인.
4. **조치:** `public.moa_inquiries` 테이블과 해당 시퀀스에 한정해 필요한 권한 부여. 기존 T06·T08 테이블은 수정 대상으로 삼지 않음.
5. **재시험:** 권한 조회값이 모두 `true`로 변경됨을 확인. 동일 가상 JSON 요청에서 HTTP `201 Created`를 확인.
6. **실제 연결 확인:** Make AI Agent 처리 경로에서 `MOA-FORM-9`, DB ID `3`이 생성되고, Supabase에서 문의 원문·분류 `공통 안내`·안내ID `MOA-G003`·검토 상태 `검토 대기`를 대조함.

**주의:** `MOA-G003`은 테스트에서 승인 상태로 전환한 **가상 안내자료**이며, 이 1건의 저장 성공이 전체 서비스의 안정성이나 실제 사용자 성과를 의미하지 않는다.

## 7. 이후 검증 및 포트폴리오 증빙 계획

- **운영자 인증:** Supabase Auth 비밀번호 복구 후 로그인 성공, 운영자 UID 불일치 및 비인증 요청 차단 여부 확인
- **실제 검토 흐름:** Supabase 문의 조회 → 답변 수정 → 검토 승인 → 상태 변경 → 새로고침 후 DB 반영 대조
- **Fallback:** 근거 부족 문의에 `ai_draft` 없이 `검토 대기`로 저장되는지 확인
- **식별자 정합성:** Response ID 기반 도입 후 동일 응답 재처리와 원본 대응 관계 검증
- **최종 산출물:** 기획 변경 전후 비교, Make 실행 화면, Google Sheets/DB 결과, 오류 로그, Git 커밋 기록, QA 표, 데모 영상·발표자료

### 확보·확인한 근거 예시

- Make AI Agent의 `search_approved_guide`·`register_confirmation_request` 도구 실행 화면
- Google Sheets의 승인 전후 안내 및 문의관리 대장
- Make HTTP `201` 응답 (`status: created`, `id: 3`, `source_ref: MOA-FORM-9`)
- Supabase DB ID 3의 문의 원문·분류·안내ID·상태
- `42501` 로그, 권한 검사 `false` → 수정 후 `true`
- 사용자 PowerShell에 표시된 GitHub Push 성공 로그 및 개발 문서 파일명

## 8. 취업용 핵심 메시지 — 사실 기반 요약

> MOA를 개발하면서 AI가 자료에 없는 메뉴를 안내하거나, 문의 분류와 실행 행동이 서로 어긋나는 문제를 직접 확인했습니다. 이에 승인된 안내 원문을 사용하는 경로와 분류·행동을 함께 검증하는 조건을 적용하고 결과를 재시험했습니다. 또한 실제 AI 처리 결과를 Supabase에 저장하는 과정에서 권한 오류를 로그와 SQL 검사로 추적해 수정했고, DB 저장값까지 확인했습니다. 현재 운영자 웹에서 실제 결과를 조회·승인하는 기능과 고유 문의ID 전환은 추가 검증 중입니다.

**기록 원칙:** 확인된 실행과 화면만 성과로 표시한다. 기획 의도·AI 제안·직접 수행·실제 검증을 분리한다. 모든 자료는 가상 QA 환경을 기반으로 하며, 확인되지 않은 수치·사용자 반응·도입 성과를 만들어내지 않는다.
